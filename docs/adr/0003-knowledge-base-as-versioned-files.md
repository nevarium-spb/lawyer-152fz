# ADR-0003. База норм — файлы в git + полнотекстовый поиск, без векторной БД

- Статус: принято
- Дата: 2026-10-23

## Контекст

Корпус небольшой: 152-ФЗ, ст. 13.11 КоАП, профильные постановления правительства, приказы и разъяснения РКН —
сотни статей, а не миллионы документов. Важнее точность и прослеживаемость редакций, чем семантический поиск.
Сервер должен работать офлайн и стартовать быстрее секунды.

## Решение

- Одна статья (или часть статьи) — один Markdown-файл в `packages/knowledge/data/<акт>/`.
- Frontmatter: `id`, `act`, `heading`, `editionDate`, `sourceUrl`, `verifiedAt`, `sha256`. Схему проверяет zod при сборке.
- Сборка создаёт индекс полнотекстового поиска (MiniSearch, BM25) с русским стеммером; индекс вшивается в бандл.
- Версия базы — `kb-ГГГГ.ММ.ДД` по дате последней сверки; печатается в каждом отчёте.
- Обновление базы — через pull request с диффом текста нормы: правка закона видна построчно в истории git.
  Это наш аналог «миграций» (роль DBA в процессе).
- Онлайн-проверка актуальности (`check_norm_freshness`) сравнивает сохранённое с официальным источником;
  при недоступности источника возвращает `unknown`, а не «всё хорошо».

## Последствия

- \+ Прозрачная история изменений закона; ревью правок как кода.
- \+ Нет инфраструктуры (векторная БД, эмбеддинги, ключи).
- − Поиск по синонимам слабее семантического; компенсируется тем, что модель формулирует несколько запросов.
- − Нужен человек, сверяющий тексты (`verifiedAt`).

## Отвергнутые варианты

- **Векторная БД + эмбеддинги** — избыточно для корпуса такого размера, нужен внешний сервис или тяжёлая модель.
- **Только онлайн-поиск** — медленно, нестабильно, нетестируемо.
- **Знания модели** — риск устаревших и выдуманных норм.
