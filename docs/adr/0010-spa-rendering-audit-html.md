# ADR-0010. Сайты на SPA: DOM от браузера хоста (`audit_html`), без браузера в плагине

- Статус: принято
- Дата: 2026-10-28
- Закрывает: риск R3 в [ARCHITECTURE.md](../ARCHITECTURE.md), спайк S1 в [PLAN.md](../PLAN.md)

## Контекст

Статическая загрузка (`fetch` + разбор HTML) не видит формы, которые SPA рисует в браузере: в ответе сервера только
пустой `<div id="root">` и скрипты. Таких сайтов много, в том числе сайт Невариум (Vite + React) — цель проверки T5.8.
У плагина нет `node_modules`: сервер поставляется одним файлом `server/index.mjs` (ADR-0005).

Спайк S1 (2026-10-28, `playwright-core` 1.64.1, esbuild 0.28.2, Node 26, Windows 11) проверил два варианта.

**(а) `playwright-core` и системный Chrome.**

- Из `node_modules` всё работает: `chromium.launch({ channel: 'chrome' })` отрисовал форму, созданную скриптом, за 429 мс.
- **В один файл не собирается.** esbuild требует необязательный `chromium-bidi`. Если его исключить, бандл (3,8 МБ)
  падает при старте с `ERR_AMBIGUOUS_MODULE_SYNTAX`: Playwright во время работы читает свой `package.json` и ресурсы
  через `__dirname`. Официально сборка Playwright бандлером не поддерживается.
- Рабочий путь один — положить `playwright-core` отдельной папкой в плагин. Это +14 МБ к плагину (сейчас 3,4 МБ)
  и зависимость от установленного Chrome или Edge.
- **Второй сетевой канал в обход SSRF-защиты (ADR-0006).** Браузер сам загружает подресурсы и выполняет скрипты
  проверяемого сайта; каждый такой запрос пришлось бы перехватывать (`page.route`) и проверять IP. Это та же
  защита, что в `PageLoader`, но поверх чужого движка — больше поверхности атаки и сложнее тестировать.

**(б) Инструмент `audit_html`.** Хост (Claude Code, другой MCP-клиент, позже бот) передаёт HTML страницы,
уже отрисованный своим браузером: встроенная панель браузера, `/browse`, Claude in Chrome, DevTools, «Сохранить как».
Сервер разбирает его тем же анализатором, что и статическую загрузку, и прогоняет те же правила.

## Решение

1. **В M5 делаем (б):** инструмент `audit_html({ url, html })` — `url` нужен для доказательств и проверки HTTPS,
   сеть сервер не трогает. Размер HTML ограничен.
2. **Статический `audit_site` распознаёт оболочку SPA** (пустой корневой контейнер, мало текста, крупные скрипты)
   и пишет в `notChecked`: «страница отрисовывается скриптами — передайте DOM из браузера через `audit_html`
   или проверьте исходники через `audit_codebase`». Ложного «нарушений нет» по пустой оболочке не бывает.
3. **Параметр `render` порта `SiteScanner` оставляем**, но в M5 он не включает браузер: при `render: true` сканер
   добавляет в `notChecked` ту же подсказку. Вариант (а) возвращаемся рассматривать, только если `audit_html`
   окажется неудобен на практике (отзывы после v0.2) — тогда отдельным ADR с перехватом запросов браузера.
4. Скилл `pd-audit` подсказывает модели: для SPA сначала получить DOM своим браузерным инструментом и вызвать
   `audit_html`; исходники проекта — через `audit_codebase`.

## Последствия

- \+ Плагин остаётся одним файлом без зависимостей; SSRF-защита в одном месте — в `PageLoader`.
- \+ `audit_html` работает и там, где у сервера нет сети к цели: сайт за VPN, авторизацией или антиботом —
  пользователь открывает его в своём браузере.
- \+ Тот же инструмент пригодится боту: пользователь может прислать сохранённую страницу.
- − Нужен браузерный инструмент у хоста; без него SPA проверяется только по исходникам (`audit_codebase`).
- − Cookie, которые ставят скрипты, и сетевые запросы к счётчикам `audit_html` не видит — только разметку DOM.
  Это записывается в `notChecked`.

## Отвергнутые варианты

- **Бандл с `playwright-core`** — не собирается в один файл (см. спайк).
- **`playwright-core` отдельной папкой в плагине** — +14 МБ, системный браузер как зависимость, второй канал
  в обход SSRF-защиты. Отложено до реальной потребности.
- **Скачивать Chromium при первом запуске** — сеть и сотни мегабайт на машине пользователя без его ведома.
