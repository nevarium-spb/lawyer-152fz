Дата редакции каждого акта — в `data/<акт>/act.json` (`editionDate`), версия базы — по последней сверке (`kb-ГГГГ.ММ.ДД`).

## Как устроены файлы

- `data/<акт>/act.json` — метаданные: название, вид (`law` / `code` / `decree`), идентификатор документа и редакции на портале.
- `data/<акт>/art-<N>.txt` или `item-<N>.txt` — одна статья или пункт: YAML-заголовок (`id`, `heading`, `editionDate`, `sourceUrl`,
  `verifiedAt`, `sha256`, `notes`) и официальный текст. Простой текст, а не Markdown: разметка исказила бы закон.
- Части статей (`152-fz/art-18/part-5`) выводятся из текста при загрузке, отдельными файлами не хранятся.
- `notes` — пометки портала «(В редакции…)». Это справка, в текст нормы не входит.

**Файлы в `data/` не редактируются руками**: `sha256` в заголовке должен совпадать с текстом, иначе база не загрузится.

## Обновление

```bash
pnpm kb:import            # все акты
pnpm kb:import 152-fz     # один акт
```

Скрипт загружает актуальную редакцию, раскладывает её по файлам и проверяет всю базу. Изменения закона видны
в `git diff` и проходят ревью в pull request ([ADR-0011](../../docs/adr/0011-official-source-actual-pravo.md)).

## Будущие редакции

Портал публикует и принятые, но не вступившие в силу редакции. В базе — только действующая; `check_norm_freshness`
сообщает о будущих датах. Когда будущая редакция вступает в силу, нужен `pnpm kb:import <акт>` и патч плагина.
Сравнение будущих редакций с базой по каждой норме — в протоколах сверки ([T7.2](../../docs/audits/2026-10-29-kb-verify-t7.2.md)).
