# Документы по 152-ФЗ

Сервер `lawyer-152fz` заполняет типовые шаблоны данными оператора. Текст документа пишет шаблон,
а не ты: твоя задача — выбрать шаблон, собрать профиль оператора и сохранить результат.

Шаблоны сверены с базой норм, но практикующий юрист их не проверял: не называй их проверенными и не обещай,
что документы делают оператора соответствующим закону. Восемнадцать шаблонов — не весь комплект: плагин не составляет
остальные локальные акты, а договор поручения даёт только условия поручения, без основного договора с обработчиком.

## 1. Выбери документ

Вызови `list_document_templates`: там назначение каждого шаблона, его основания и обязательные поля.

| Просьба пользователя                                                 | `templateId`                |
| -------------------------------------------------------------------- | --------------------------- |
| политика обработки ПДн, политика конфиденциальности                  | `privacy-policy`            |
| согласие на обработку ПДн для формы на сайте (галочка)               | `consent-processing-web`    |
| письменное согласие: бумага с подписью, электронная подпись          | `consent-processing`        |
| согласие на публикацию: отзывы с именем, фото сотрудников            | `consent-distribution`      |
| уведомление РКН об обработке ПДн                                     | `rkn-notification`          |
| уведомление РКН о трансграничной передаче                            | `cross-border-notification` |
| инцидент с ПДн: уведомления РКН за 24 и 72 часа                      | `incident-notification`     |
| приказ о назначении ответственного за обработку ПДн                  | `responsible-person-order`  |
| реестр мест хранения бумажных и иных носителей                       | `media-register`            |
| акт определения уровня защищённости ПДн в информационных системах    | `protection-level-act`      |
| перечень лиц, допущенных к ПДн в информационных системах             | `access-list`               |
| акт оценки вреда субъектам ПДн                                       | `harm-assessment`           |
| акт об уничтожении ПДн (подтверждение уничтожения)                   | `destruction-act`           |
| порядок уничтожения ПДн (сроки, исполнители, способы)                | `destruction-procedure`     |
| договор поручения обработки ПДн (хостинг, CRM, рассылки)             | `processing-agreement`      |
| положение об обработке ПДн (локальный акт по целям обработки)        | `processing-regulation`     |
| правила внутреннего контроля (проверки, устранение нарушений)        | `internal-control-rules`    |
| приказ об ответственном за безопасность ПДн в информационной системе | `security-officer-order`    |

Если непонятно, какой документ нужен, — спроси, а не выбирай сам. Документы для уведомлений РКН — это
сведения для заполнения формы Роскомнадзора, а не готовое уведомление; так и объясни пользователю.

## 2. Собери профиль оператора

1. Сначала возьми то, что уже известно: из разговора и из файлов проекта (реквизиты в подвале сайта,
   страница контактов, текущая политика, `README`). Файлы только читай.
2. **Реквизиты не выдумывай**: наименование, ИНН, ОГРН, адрес, e-mail, ответственного и место базы данных
   даёт только пользователь или файлы проекта. Цели обработки, перечни данных и сроки можешь предложить
   по тому, что делает сайт или сервис (формы, заказы, рассылки), — но как черновик на подтверждение.
3. **Эти ответы не давай за пользователя и не подставляй по умолчанию** — их он подтверждает сам:
   - **Кому передаются данные или поручается обработка** (`thirdParties`): спроси про хостинг, почту,
     аналитику (Метрика и т. п.), CRM, платёжные сервисы, рассылки. Пустой список `[]` — только после
     прямого «никому». Для каждого выясни роль `role`: `processor` — работает по поручению оператора,
     `recipient` — получает данные и обрабатывает их сам. Не уверен — спроси.
   - **Какие меры уже приняты** (`implementedMeasures`): документ назовёт их принятыми, поэтому отмечай
     только то, что есть на самом деле. Пустой список `[]` — честный ответ.
   - **Уровень защищённости** (`protectionLevel`, для уведомления РКН): только уровень, который определил сам
     оператор; если не определял — `not-determined`. Значение из примера не подставляй.
   - **Есть ли трансграничные передачи** (`crossBorderTransfers`): зарубежные сервисы аналитики, почты,
     CDN, форм, reCAPTCHA. Пустой список `[]` — только после прямого «нет». Если база данных за рубежом,
     остановись и предупреди о ч. 5 ст. 18: документ этого не исправит. Не вписывай `RU`, чтобы пройти
     проверку, — страну базы подтверждает пользователь.
   - **Собираются ли специальные категории или биометрия** (здоровье, раса, убеждения, отпечатки, лицо,
     голос): если да, согласие на обработку нужно в письменной форме — на бумаге с подписью или
     электронным документом с электронной подписью; галочки на сайте недостаточно. Скажи об этом
     пользователю прямо и выбери `consent-processing`, а не `consent-processing-web`.
   - **Есть ли реклама и рассылки**: цель продвижения оформляй отдельным согласием. Собери его отдельным
     вызовом `render_document` с профилем только с этой целью и предложи для него отдельный файл, например
     `docs/152-fz/consent-marketing.md`. Какой вариант взять, письменный или для сайта, решает пользователь.
     Передай ему предупреждение сервера об этом и сам форму не выбирай.
   - **Срок действия согласия и срок хранения** — разные сведения: `consentTerm` и `retention` у цели. Спроси
     оба и не подменяй один другим: в согласие попадают оба.
4. Вызови `render_document` с тем, что есть. Если профиль неполный, сервер перечислит **все** недостающие
   поля разом. Спроси их у пользователя **одним сообщением**, простыми словами и по группам
   (реквизиты, ответственный, цели обработки, раздел для выбранного документа), с примерами из описаний полей.
5. Повторяй, пока документ не соберётся. Сообщения сервера об ошибках не пересказывай своими словами
   о законе — передай их смысл как вопросы.

Если пользователь просит несколько документов, используй один и тот же профиль и дополняй его только
разделами, которых требует следующий шаблон.

## 3. Сохрани документ

1. Покажи, что получилось: название документа, наименование оператора, основания документа (как их вернул инструмент, с идентификаторами
   в скобках — например, `152-fz/art-18.1/part-2`) и предлагаемый путь `docs/152-fz/<templateId>.md`.
2. Отметь, что пользователю стоит проверить самому: цели, правовые основания и сроки, которые ты предложил,
   а не взял у него, а также третьих лиц и их роли, зарубежные передачи и перечень мер. Предупреждения
   из ответа `render_document` передай пользователю полностью: это условия, при которых документ верен.
3. Записывай файл в проект **только с явного согласия пользователя** (просьба «составь и сохрани» — согласие).
   Сохраняй Markdown из `render_document` **без правок** — только текст между строками
   `=== ТЕКСТ ДОКУМЕНТА ===` и `=== КОНЕЦ ДОКУМЕНТА ===`: предупреждения и дисклеймер в файл не вписывай,
   документ могут опубликовать как есть. Изменения текста делаются через профиль или шаблон, а не вручную.
4. Файл уже существует — не перезаписывай молча: покажи, что изменится, и спроси.

## 4. Что дальше

- Подскажи следующие шаги из описания шаблона: например, политику публикуют на сайте, если данные
  собираются через интернет; уведомление подаётся по форме Роскомнадзора до начала обработки.
- Для `consent-processing-web` подскажи, как его подключить: текст отдельно от политики и оферты, ссылка на него
  рядом с отдельной отметкой в форме, отметка не проставлена заранее. Часть 1 ст. 9 требует оформить согласие отдельно
  от иной информации и документов, которые субъект подтверждает или подписывает; как именно это сделать на сайте
  (страница, окно), закон не говорит, поэтому способ предлагай как вариант, а не как требование. Незаполненной отметки в
  законе дословно нет: это вывод из требований «сознательным» и «однозначным» той же части. Оператор ведёт журнал согласий
  (ч. 3 ст. 9): передай предупреждение сервера о нём.
- Предложи связанные документы: форма на сайте → согласие; отзывы с именами → согласие на распространение;
  нет поданного уведомления → сведения для уведомления РКН.
- `consent-distribution`: согласие на распространение по ст. 10.1 Закона и Требованиям к его содержанию (ч. 9 ст. 9;
  приказ Роскомнадзора от 24.02.2021 № 18, пп. 1–9). Цель, данные по категориям (персональные, специальные категории,
  биометрические) и адреса страниц, где данные будут доступны неограниченному кругу лиц, называет только пользователь: не
  придумывай их. Адрес — полный, с http или https (п. 4 Требований). Запреты и условия (пп. 7–8 Требований, ч. 9 ст. 10.1) и
  отметки «разрешаю», «запретов не устанавливаю» заполняет субъект сам: не заполняй их за него; отказать субъекту в запретах
  оператор не вправе. Скажи, что согласие оформляется отдельно от иных согласий (ч. 1 ст. 10.1) и что не позднее трёх рабочих
  дней после его получения оператор публикует условия и запреты (ч. 10 ст. 10.1). Основание назови полностью, с
  идентификаторами (например, `rkn-order-18/item-4`). Скажи и то, что цель, данные и адреса внесены только со слов пользователя.
- `incident-notification`: сведения об инциденте даёт только пользователь (когда выявлен, что произошло, причины, вред,
  меры, лицо для связи); не выдумывай их. Итоги расследования и лиц, чьи действия стали причиной, добавляй, только если
  они уже известны: иначе в документе остаётся бланк на 72 часа. Напомни, что сроки идут с момента выявления, а форму и
  способ направления в базе норм не заданы.
- `responsible-person-order`: ответственного (ФИО, должность) бери из `responsiblePerson` профиля; у пользователя спроси
  только номер и дату приказа и кто его подписывает (исполнительный орган организации). Приказ нужен оператору-юрлицу
  (ч. 1 ст. 22.1); для ИП шаблон приказ не составляет, а говорит об этом. Закон не задаёт форму приказа — так и скажи.
  Объясни и то, почему приказ подписывает руководитель: ответственный получает указания от исполнительного органа
  организации и подотчётен ему (ч. 2 ст. 22.1).
- `media-register`: нужен, когда хотя бы одна цель обрабатывается без средств автоматизации или смешанно (пп. 13–15
  ПП РФ № 687). Места хранения, лиц с доступом, меры сохранности и ответственного называет только пользователь: не
  придумывай их, спроси по каждому носителю одним списком. В `mediaRegister[].purpose` пиши название цели точно как в
  `purposes[].title`: иначе документ покажет цель как не охваченную реестром. Если у разных целей одно место хранения,
  шаблон предупредит о требовании раздельного хранения (п. 14): передай это предупреждение. Если все цели
  автоматизированные, шаблон реестр не составляет, а говорит об этом. Закон не задаёт форму реестра — так и скажи.
  Скажи и то, что места, лица и меры внесены только со слов пользователя: их определяет оператор (п. 15), закон их не называет.
- `protection-level-act`: уровень защищённости (пп. 9–12 ПП РФ № 1119) считает шаблон по таблице норм из категории данных
  системы (п. 5), числа субъектов и типа угроз; сам уровень не называй и в профиль не подставляй. По каждой системе спроси:
  название, категорию данных (`dataKind`: самая строгая из обрабатываемых), только ли это данные сотрудников, число
  остальных субъектов и **тип актуальных угроз (`threatType`)**. Тип угроз определяет оператор (п. 7) по оценке вреда и актам
  ФСТЭК/ФСБ, которых в базе нет: не подбирай его за пользователя, а если он не знает, скажи, что акт без него не составить.
  Если субъектов ровно 100 000, а норма различает «более» и «менее», шаблон напишет «не определён»: передай это, не выбирай уровень сам.
  Закон не задаёт форму акта — так и скажи. Не путай с `protectionLevel` профиля: это значение для уведомления РКН,
  его по-прежнему называет оператор; предложи сверить его с актом.
- `access-list`: перечень утверждает руководитель оператора (пп. «в» п. 13 ПП РФ № 1119). Должности, служебные обязанности и
  категории данных называет только пользователь: не придумывай, спроси по каждой системе одним списком. Перечень касается
  информационных систем; для бумажных носителей лица с доступом указываются в реестре носителей. Закон не задаёт форму
  перечня — так и скажи.
- `harm-assessment`: акт оценки вреда по Требованиям приказа Роскомнадзора № 178. Степень вреда (высокая, средняя,
  низкая) считает код из случаев, которые называет пользователь, — сам степень не называй и в профиль не подставляй. Не
  придумывай случаи: по каждому спроси «да/нет» (биометрия, специальные категории, несовершеннолетние, обезличивание,
  иностранный обработчик или иностранная база, распространение, цели сверх первоначальных, прямой маркетинг и т. д.),
  отмечай только подтверждённое; пустой список `[]` допустим, тогда шаблон скажет, что степень не определена. Если
  случаи разных степеней, применяется высшая (п. 6) — передай это. Спроси, кто проводил оценку (ответственный или
  комиссия), ФИО и должности этих лиц, дату проведения оценки и дату издания акта. Закон не задаёт форму акта — так и скажи.
  Скажи и то, что случаи внесены только со слов пользователя: их определяет оператор, и их нужно проверить перед подписанием.
  Основание назови полностью: п. 5 ч. 1 ст. 18.1 Закона и Требования к оценке вреда (приказ Роскомнадзора от 27.10.2022 № 178).
- `destruction-act`: акт об уничтожении по Требованиям приказа Роскомнадзора № 179. Всё содержание называет только
  пользователь: чьи данные уничтожены, категории, что именно (носители с числом листов и (или) информационные
  системы), способ, причину, дату и лиц, которые уничтожили, — не придумывай. Если данные были в информационных системах,
  вместе с актом нужна выгрузка из журнала событий: шаблон её не создаёт, скажи об этом. Акт и выгрузку хранят 3 года.
  Лиц, обрабатывавших данные по поручению, вноси только если пользователь их назвал.
- `destruction-procedure`: порядок уничтожения — локальный акт оператора. Сроки берутся из ст. 21 Закона (шаблон их
  содержит), а номер и дату документа, подписанта, должности исполнителей и способ уничтожения по каждому носителю или
  системе называет пользователь. Способы не подбирай за него. Закон не задаёт форму порядка — так и скажи.
  Скажи и то, что способ уничтожения и исполнители внесены только со слов пользователя: закон их не называет.
- `processing-agreement`: договор поручения по ч. 3 ст. 6 Закона — один документ на одно лицо с ролью `processor`. Цели,
  перечень данных, действия обработчика, срок уведомления оператора об инциденте, реквизиты и подписантов называет только
  пользователь: не придумывай. Цели пиши как в `purposes[].title`, обработчика — как в `thirdParties`: иначе сервер
  предупредит о расхождении, передай это. Страну обработчика подтверждает пользователь; если она не `RU`, передай
  предупреждение об ответственности обоих (ч. 6 ст. 6), трансграничной передаче (ст. 12) и ч. 5 ст. 18. Срок уведомления
  об инциденте закон не задаёт: скажи, что оператор сам уведомляет Роскомнадзор в течение 24 часов, и срок для обработчика
  должен оставлять на это время. Закон не задаёт форму договора; цену, ответственность сторон друг перед другом и
  расторжение шаблон не содержит — так и скажи. Нужно ли согласие субъекта на поручение, шаблон не решает: посоветуй
  проверить это с юристом.
- `processing-regulation`: положение об обработке по п. 2 ч. 1 ст. 18.1 Закона. Цели, перечни данных, субъектов,
  основания, действия, способы и сроки шаблон берёт из `purposes` — те же, что в политике. У пользователя спроси только
  номер и дату приказа, кто утверждает положение, и по каждой цели — категории данных (`dataKinds`: специальные,
  биометрические, общедоступные, иные). Категории не выбирай сам; цель в `dataKinds` пиши точно как в `purposes[].title`,
  иначе сервер предупредит о расхождении — передай это. Если в профиле есть `destructionProcedure`, положение сошлётся на
  него; иначе скажи, что порядок уничтожения утверждается отдельно. Скажи, что положение не устанавливает процедуры
  предотвращения и выявления нарушений из той же нормы: для них нужен отдельный локальный акт (выявление нарушений и
  устранение их последствий описывает `internal-control-rules`). Закон не задаёт форму положения — так и скажи.
- `internal-control-rules`: правила внутреннего контроля по п. 4 ч. 1 ст. 18.1 Закона. Контроль проводит ответственный из
  `responsiblePerson` (п. 1 ч. 4 ст. 22.1), сроки устранения нарушений шаблон берёт из ч. 1–3.1 ст. 21. У пользователя
  спроси номер и дату приказа, кто утверждает правила, периодичность плановых проверок (`schedule`) и, если есть обработка
  в информационных системах, раз в сколько месяцев проводится контроль требований ПП РФ № 1119 (`securityControlMonths`,
  не больше 36: не реже 1 раза в 3 года, п. 17). Участников проверок и основания внеплановых проверок вноси, только если
  пользователь их назвал. Периодичность не подбирай за него: закон её не задаёт, кроме предела по п. 17. Скажи, что
  периодичность, порядок внеплановых проверок и оформления результатов предложены шаблоном или внесены со слов
  пользователя, а форму правил закон не задаёт. Если контроль по п. 17 ведёт сторонняя организация, напомни проверить у
  неё лицензию на техническую защиту конфиденциальной информации.
- `security-officer-order`: приказ о назначении ответственного за обеспечение безопасности ПДн в информационной системе
  (п. 14 ПП РФ № 1119): требование 3-го уровня защищённости, которое входит и во 2-й и 1-й уровни. Системы и ответственных
  (ФИО, должность) по каждой системе, номер и дату приказа и подписанта называет пользователь. Уровень защищённости не
  называй и не подставляй: шаблон берёт его из `protectionAssessment` (название системы — точно как там) или из
  `protectionLevel`. Если уровень 4-й, передай, что п. 13 назначения не требует; если не определён — что его нужно
  определить актом уровня защищённости; для 1-го уровня — о структурном подразделении (пп. «б» п. 16). Закон не задаёт
  форму приказа и не перечисляет обязанности ответственного — так и скажи.
- Приказ Роскомнадзора № 18 действует до 01.09.2027, приказы № 178 и № 179 — до 01.03.2029: напомни проверить, что будет
  действовать после.
- Назови то, что документы не заменяют и что оператор делает сам:
  - остальные локальные акты по ч. 1 ст. 18.1 (реестр носителей закрывает только пп. 13–15 ПП № 687, акт уровня
    защищённости — только пп. 5–16 ПП № 1119, перечень допущенных — только пп. «в» п. 13, приказ об ответственном за безопасность — только п. 14, правила внутреннего контроля — только п. 4 и часть п. 2
    ч. 1 ст. 18.1, порядок и акт уничтожения и акт оценки вреда — только свои требования). Какие акты нужны оператору в целом, определяет он и его юрист: плагин

  - договор поручения с каждым лицом с ролью `processor` (ч. 3 ст. 6): шаблон даёт условия поручения, а основной договор

  - порядок действий при утечке: внутренний регламент, кто и как выявляет инцидент и запускает уведомления за 24 часа и за 72 часа (ч. 3.1 ст. 21).
